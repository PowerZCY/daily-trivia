# Daily Trivia 首页方案

## 文档目的

这份文档用于沉淀 Daily Trivia 首页的当前实现思路、体验结构与 SEO 设计原则。

它不是一份纯技术实现清单，而是一份面向产品、设计和内容运营协作的首页说明。重点回答三个问题：

- 首页为什么这样组织
- 首页内容如何被搜索引擎理解
- 当前数据边界如何支撑体验稳定性

## 首页角色

Daily Trivia 首页承担的是“每日入口页”的职责，而不是完整内容库本身。

它要完成的不是一次性承载所有历史价值，而是清晰地完成三件事：

- 向用户介绍今天可以做什么
- 让用户立即进入当天答题
- 把历史题目以稳定、可浏览、可点击的方式沉淀下来

因此，首页的价值主要来自“今天的参与感”和“历史内容的清晰入口”，而不是传统营销站式的大段模块堆叠。

## 当前页面结构

当前首页保留三个主要部分：

- `FingerprintStatus`
- `Hero`
- `SeoContent`

其中真正承载首页主体体验的是 `Hero`。它不是单一视觉横幅，而是首页主容器，内部按体验优先级组织为三层：

1. 顶部介绍区
2. 当日答题区
3. 历史题目区

这种结构的好处是很直接的：

- 首屏先建立“Daily Trivia 是什么”
- 紧接着把用户带入今天的 5 道题
- 在完成核心任务之后，再向下承接历史浏览

首页不再保留模板式的营销区、画廊区或与答题目标无关的内容板块。整体信息密度更集中，页面意图更明确。

## Hero 的设计定位

Hero 在这里不是传统意义上的宣传 Banner，而是首页的叙事骨架。

它承担的是一种“轻介绍 + 强行动 + 可回看”的页面节奏：

- 标题与说明负责建立语义，告诉用户这是每日更新的 Trivia 入口
- 中段答题模块负责承接当天最重要的行为
- 下段历史列表负责形成连续性，让用户知道这个产品并不是一次性的

视觉上，Hero 不是深色整屏压迫式舞台，而是更贴近当前站点的通透感与内容阅读感。它强调的是清晰、节奏和可点击性，而不是情绪化装饰。

## 当日答题体验

首页的核心内容仍然是“当天 5 道题”。

这部分体验的原则是：

- 首次进入就能看到真实题目内容
- 不需要额外跳转即可开始作答
- 完成后在原位置看到答题报告

答题模块不是独立页面入口的缩略卡片，而是真正可直接交互的主内容区。这样做有两个明显收益：

- 首屏行动路径更短，用户不需要二次决策
- 当天题目的题干可以直接进入服务端输出的 HTML，形成更好的内容可见性

完成答题后，报告会在原区域内替换显示，而不是把结果拆到另一个首页板块中。这让用户的行为路径更完整，也避免页面出现“两套主内容同时竞争注意力”的问题。

## 历史题目区

历史题目区的职责不是复刻当天答题区，而是提供一种轻量、稳定、连续的浏览体验。

当前历史列表每张卡片只保留三类信息：

- 日期
- Day 编号
- 当天首题题干

这种设计是刻意做轻的。它避免把历史区做成复杂的信息墙，同时保留了足够的语义密度，让用户能快速判断是否想进入那一天。

历史列表还会基于本地完成记录给出轻量完成态提示，但这种提示只是体验增强，不影响服务端输出的主内容。

## 日期与节奏规则

当前产品的日期规则非常明确：

- 统一按 `UTC+0` 计算每日题目
- `2026-04-01` 为 Day 1
- Day 编号通过日期推导，不单独存储
- 当天题目固定为 5 道，按排期顺序展示

这套规则的价值在于稳定。它让首页、历史页、埋点、持久化与 SEO 描述都建立在同一套日期语义上，减少认知分叉。

## 首页展示规则

首页不是简单地“取今天的数据然后直接渲染”，它有一套明确的展示判断顺序，用来保证页面每天都有一致的表达方式。

### 当日题目的展示规则

首页主答题区优先展示“今天可发布的最新一组题目”。

这里的判断逻辑可以概括为：

1. 先按 `UTC+0` 计算今天的日期
2. 在排期表中查找不晚于今天、且被标记为每日首题的候选日期
3. 按日期从新到旧回看
4. 找到第一组能够组成完整答题内容的日期后，作为首页主答题区内容输出

这样做的目的不是制造复杂性，而是保证首页在排期存在、但最新一天的完整题目详情暂时不可用时，仍然有机会退回到最近一组可展示内容，而不是直接塌成空白。

从体验上看，首页始终在表达的是“现在最应该被用户看到的一组 Daily Trivia”，而不是机械地只认自然日。

### Day 编号的推导规则

Day 编号不单独存库，而是通过日期计算得到。

它的推导方式可以理解为：

- 把 `2026-04-01` 视为 Day 1
- 当前日期与这个起点之间每相差一天，Day 编号递增 1

这套小算法的意义在于：

- 不需要额外维护一列可能出错的序号
- 首页、历史页、metadata 和文案系统都可以共享同一个编号逻辑
- 只要日期稳定，Day 编号就天然稳定

### 当日题目的排序规则

当天一组题目固定为 5 道，按 `sort_order` 从小到大展示。

这意味着首页看到的题目顺序并不是客户端临时决定的，而是排期阶段已经定义好的叙事顺序。首页负责忠实输出这种顺序，客户端只负责在交互过程中推进作答与反馈。

## 历史题目规则

历史区也有自己非常明确的展示边界，它不是“把所有历史题全文搬上首页”，而是只提取最适合列表浏览的摘要信息。

### 历史列表的入选规则

历史列表中的每一天，只取被标记为 `as_first = 1` 的那条记录作为当天代表。

这意味着首页历史区的最小展示单位不是“单题”，而是“某一天的代表性入口”。

这种规则有两个直接好处：

- 首页不会被 5 倍数量的题目冲垮
- 每个日期都能以一致的方式被表达和点击

### 历史题题干的展示规则

历史卡片不再依赖第三方详情服务去回查首题题干，而是直接使用本地排期表里的 `question` 字段。

换句话说，历史区当前采用的是一种“本地摘要优先”的设计：

- 首页只需要一句足够表达当天主题的题干
- 这句题干由本地数据直接提供
- 运营可以介入维护这句展示文本的质量

这让历史列表更像一个稳定的内容目录，而不是一个对外部题库强依赖的临时拼装结果。

### 历史列表的时间范围规则

历史列表只展示早于今天的内容，不与主答题区争抢“今天”这个唯一核心位置。

也就是说：

- 今天的题目留给首页主区域承载
- 过去的日期进入历史区沉淀

这种切分让首页的主次关系非常清楚，不会出现“今天既在上方做主模块、又在下方重复出现在历史列表里”的内容重叠。

### 历史卡片的排序规则

历史日期按时间从近到远排列。

这是一种很自然的阅读顺序：

- 用户最先看到最近几天
- 越往下越进入更早的归档内容

它符合“从最新回看”的浏览心智，也更适合首页作为连续更新产品的内容节奏。

## 首页数据组织原则

首页当前已经不再直接把所有后端细节暴露在页面组件里，而是通过首页专用的数据装配边界组织内容。

从设计上理解，这意味着：

- 首页只关心“今天的题目”和“历史列表”这两种内容
- 页面层不需要感知题目详情来自哪里
- 数据来源可以演进，但首页叙事结构保持稳定

这对于后续演进很重要。无论未来引入缓存、分页还是新的题目来源，首页本身都不需要反复改变表达方式。

## 当前数据边界

目前首页内容已经被拆成两条相对清晰的路径：

### 1. 当日题目

当天题目仍然需要完整的题目结构，因此服务端会基于排期拿到题目详情，再将完整内容输出给答题模块。

这条链路承载的是：

- 题干
- 选项
- 正确答案
- explanation
- 分类等完整信息

它对应的是首页最强的交互内容，因此仍然需要完整题目模型。

### 2. 历史列表

历史列表现在已经明显收轻。

它只需要当天首题题干，因此不再依赖第三方详情服务去拼首题展示，而是直接使用本地排期表中的 `question` 字段。

这次变化很关键，因为它让首页历史区具备了更稳定的内容基础：

- 历史卡片题干可以直接稳定输出到 HTML
- 首页历史区不再因为外部题库波动而空掉
- 历史内容与运维录入之间形成了更可控的关系

## SEO 设计原则

Daily Trivia 的 SEO 重点不在“让首页承担所有搜索价值”，而在于把不同页面的语义分工做清楚。

### 首页的 SEO 角色

首页更适合承接“daily trivia”“today trivia”这类带有当日意图的搜索需求。

它的价值来自：

- 页面 URL 稳定
- 每天有新的服务端内容
- 当日题目和历史首题都能真实出现在 HTML 中
- 页面具备清晰的标题、说明和内链关系

### 历史页的 SEO 角色

历史日期页更适合沉淀长期内容价值。

它对应的是：

- 具体日期
- 具体题目集合
- 更稳定的历史内容入口

因此，首页与历史页不是竞争关系，而是互相分工：

- 首页承担新鲜度和入口感
- 历史页承担可归档和可沉淀的长期价值

## 当前 SEO 改善点

相比最初阶段，当前 SEO 风险已经明显下降，主要体现在三个方面。

### 1. 首页历史列表更稳定

历史卡片的题干已经从本地数据库直接提供，不再依赖第三方题目详情服务。

这意味着首页里最适合沉淀文字内容的一块区域，已经具备更稳定的服务端输出能力。

### 2. 历史详情页 metadata 已经收轻

历史日期页的 metadata 现在只基于本地首题题干生成，不再为了生成一条描述而触发完整题目详情链路。

这让页面头信息的产出更稳定，也更符合“metadata 只服务于页面语义概括”的角色。

### 3. 页面正文与 metadata 分工更清晰

当前结构已经把“完整题目内容”和“页面概括信息”拆成两种不同的数据需求：

- metadata 只需要轻量语义
- 页面主体才需要完整答题数据

这样的拆分更符合长期维护，也降低了单条重链路同时影响页面头信息与正文内容的风险。

## 仍然存在的边界

SEO 风险虽然少了很多，但并不是已经完全消失。

当前仍需明确的一点是：

- 当日答题区和历史详情页正文，仍然依赖完整题目详情能力
- 如果完整题目服务临时不可用，正文内容仍可能受影响

也就是说，当前最明显的改善发生在：

- 首页历史区
- 历史详情页 metadata

而不是整个题目详情链已经完全本地化。

这已经是一个很有价值的阶段成果，但文档上需要保持这个边界意识，避免误判为“SEO 已经完全脱离第三方依赖”。

## 交互与内容状态

首页答题体验遵循的是“服务端给内容、客户端承接过程”的分工。

服务端负责：

- 输出当天题目
- 输出历史列表
- 保证首屏文本可以直接进入 HTML

客户端负责：

- 单题作答推进
- 正误反馈
- 答题完成后的报告切换
- 本地完成态恢复
- 历史卡片完成态增强

这让首页既保留了搜索引擎可见的内容价值，也保留了答题产品应有的即时反馈感。

## 视觉与行为反馈

首页的交互反馈现在倾向于“短促、明确、不打扰”。

例如历史卡片与页内导航链接的反馈动画，当前只执行一个周期，不再持续脉冲。这种调整更符合首页内容型产品的气质：

- 给用户确认感
- 不长期占据注意力
- 不让列表区出现持续闪动的噪音

这类微交互的方向也说明首页的设计基调已经比较明确：它不是强调炫技，而是强调节奏控制。

## 当前内容模型

从产品视角理解，首页现在使用的是两种内容颗粒度：

### 完整题目颗粒度

用于当天答题和历史详情页正文，包含答题所需的完整信息。

### 摘要颗粒度

用于历史列表和历史页 metadata，只保留能建立主题认知的最小信息。

这两种颗粒度的并存，是当前首页能够兼顾体验、稳定性与 SEO 的关键。

## 后续演进方向

当前阶段的首页结构已经足够成立，后续更适合做的是“在不破坏叙事结构的前提下继续增强稳定性”。

优先级更高的方向包括：

- 为当天完整题目链路增加更稳定的缓存或预热能力
- 在历史列表增长后评估是否引入分段加载或分页
- 继续把页面语义信息与重型题目详情能力解耦
- 评估是否需要把更多稳定文本沉淀到本地数据层

这些都应该建立在现有结构上渐进推进，而不是回到把首页做成后端细节直连的状态。

## 结论

当前 Daily Trivia 首页已经从“单纯把题目塞进首页”演进到了一个更完整的内容入口模型。

它具备几个清晰特征：

- 首页叙事结构明确
- 当日答题是绝对主角
- 历史题目形成稳定沉淀
- 首页与历史页的 SEO 分工更清晰
- 历史区与 metadata 的稳定性已经明显提升

这意味着首页不再只是一个功能挂载点，而是一个具备持续内容表达能力的产品入口。
